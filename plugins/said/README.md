# SAID — Scope -> Architect -> Implement -> Debrief

A spec-driven feature-development methodology for Claude Code. SAID turns a thin idea or a messy handoff into a scoped spec, an append-only task log, a test-first implementation, and a closing retrospective — with quality + UX gates between Implement and Debrief.

This is the **engine** (stack-agnostic). Pair it with a per-stack **starter** for batteries-included setup — see [saidkit.dev](https://saidkit.dev) and [`../../starters/README.md`](../../starters/README.md).

## The phase chain

| Phase | Skills | Produces |
|---|---|---|
| **1 — Scope** | `said:scope-grill` (thin idea), `said:scope-refine` (handoff / branch / external product specs) | `scope.md` (purpose / target shape / constraints / open questions) |
| **2 — Architect** | `said:uxtoc` (optional aid — outline: design-seed early, inspect late), `said:architect`, `said:add-task` | feature spec (recreation contract) + append-only `*.tasks.md` |
| **3 — Implement** | `said:impl`, `said:review-ux` | tasks driven Todo -> Done test-first, per-task UX gate |
| **3.5 — Gates** | `said:review-qa` (hygiene), `said:accept` (acceptance contract) | pass/fail reports |
| **4 — Debrief** | `said:debrief` | retrospective + backports + shipping reports |
| **Helper** | `said:triage` | read-only root-cause investigation |
| **Observe** | `said:board` (web page by default, `--cli` terminal, `--json` data) | read-only board — where every feature sits in the phase chain, what's stalled or waiting, and the exact command that advances it |
| **Recall** | `said:retrieval` | precedent/decision-record search: what the project already decided (`CLAUDE.md`, memory, ADRs, working dirs, probes), before you propose a default |
| **Orchestrate** | `said:said` (single feature), `said:flow` (multi-lane) | drive a feature through the whole chain in one session to a printed `goal: done` signal — invoked by the `said!` / `flow!` operator macros; `said:said` can **fan out** write-disjoint tasks to concurrent `said:impl <task> arm` builders, then `said:impl <task> close` serially in main (opt-in) |

### Subagents (spawned by the skills)

- `said:scope-refine-agent` — Phase-1 parallel codebase audit + wire/visual probes.
- `said:scope-audit` — the 5-section per-directory audit shape the refine agent follows inline.
- `said:review-ux-agent` — Phase-3 per-task UX verification against your UX checklist.
- `said:gate-reviewer` - reads one step of `review-qa`, `accept` or `debrief` above `SAID.gate-reviewer-threshold` and proposes rows with file:line evidence; the gate decides and writes.

### Session roles (main sessions, launched with --agent)

Two definitions you launch as top-level sessions, not subagents the skills spawn: one supervisor directs and verifies, one or more workers build.

- `claude --name <session> --agent said:supervisor` - the supervisor: briefs the worker sessions you name, accepts a worker's report only after re-running its gate or reading its changes, and keeps your reserved calls for you: your project's own reserved list where it has one, otherwise the default list (push, merge, deploy, deletes and the like).
- `claude --name <session> --agent said:worker` - a worker: builds on the supervisor's brief, forwards your typed words to it, commits only by brief, and holds a reserved call for you instead of acting on it.

Each definition pins a model (the supervisor `fable`, the worker `opus`); `--model` on the launch line overrides the pinned model. `--name` sets the session's name, the one you give the supervisor when you name its workers.

## Quick start

1. Install the plugin (see the [marketplace README](../../README.md)).
2. Set up the repo: clone a [starter](../../starters/README.md) for your stack (scaffolding pre-filled), or supply the binding by hand per the [adoption guide](../../guides/adoption-guide.md). **The skills need this scaffolding to be useful.**
3. Start a feature: `/said:scope-grill <your idea>` (or `/said:scope-refine <handoff-doc>`), then walk the chain.

## Scope honesty — the model under the spine (read this)

- The **spine** — Scope, Architect, Implement, Debrief — is project-agnostic. It uses only file read/write, grep, and a quality-gate command it resolves at runtime. It ports to any stack (TS, Python, Go, ...).

Under that spine sits one **surface-agnostic model**. Naming it is what lets a research, CLI, server, or web lane recognize it has the same three legs — just with different content and check-modes.

**The three legs.** Every deliverable, whatever the lane, moves through three:

1. **Intent contract** — *what to build + its shape*: `scope.md` + the design contract (`docs/ux`) + the feature spec's Acceptance Criteria.
2. **Production** — *build it*: `said:impl`.
3. **Evaluation contract + independent gate** — *prove it meets intent*: `docs/qa` (the checkable criteria) + `said:review-qa` / `said:review-ux` / `said:accept` (the judges).

Bound by one **meta-invariant**: *leg 3 is derived from leg 1, pre-committed, artifact-external, and judged by someone other than leg 2.* The producer neither writes nor grades their own acceptance. Collapse evaluation into production and you get a wall of green gates that never checked the built thing against a complete contract.

**The UX contract (`docs/ux`) — the surface-contract triad.** Every lane ships a *surface* a consumer binds to through a *contract* (its `docs/ux` representation contract), and each surface needs three legs of its own: a frozen design contract, an Architect-phase step that **designs** the surface against it, and a runtime gate that **checks** the built surface against it. UX is not special — it is the *web/human-visual* instance of a general pattern. Keep the vocabulary unified ("UX" = the experience of whoever consumes the surface — a developer for an API, an agent for an MCP tool, an operator for a CLI); do **not** split it into a parallel "UX vs DX" machinery. Parameterize it by two declared lane axes — **`SAID.surface:`** (the medium the lane ships) and **`SAID.reviewers:`** (the Checkers that gate it) — instead:

| `surface:` | Consumer | Design contract | Checker (owns capture + judge) |
|---|---|---|---|
| `web` | a person | list / form / shell / field rules | `web-ux` — browser capture, comparative judge |
| `api` | a developer | REST shape, error envelope, pagination, versioning | schema-conformance oracle over an http-call capture |
| `mcp` | an agent | tool naming, input schema, idempotency, error shape | handshake + schema-probe oracle |
| `cli` | an operator | flags, exit codes, output format, `--help` | `cli-gate` — process-spawn capture, oracle judge; recomputes the lane's command line plus every `docs/evaluation/**/harness.sh` by exit code, known failures declared in `docs/evaluation/EXPECTED-FAIL` |

**The load-bearing guard:** a lane declares `SAID.surface:` (the medium) and `SAID.reviewers:` (the Checkers). The gate (`said:review-ux`) **resolves the declared reviewers and runs each** — it does **not** branch on the medium; each Checker owns its own capture + judge (browser / http-call / process-spawn ...), so an API lane is gated by its schema Checker, never Playwright-walked, reported "env-blocked", and shipped unverified. The design step (`said:architect`) reads `SAID.surface:` to author requirements against the medium — **config in the per-project binding; adding a reviewer / medium is a dropped Checker file, not a new skill per surface** (`ADR-SAID-S06` §2–3).

**The QA contract (`docs/qa`) — the evaluation harness.** `docs/qa` is the evaluation *contract*, not the gate: the frozen, per-project, *checkable* definition of what must be verifiably true to accept the work (`feature-qa-checklist.md`; the UX contract's operationalized checklist lives UX-side at `docs/ux/feature-ux-checklist.md`), run by the gates at the Implement->Debrief seam. It is `docs/ux` (+ structural ADR rules + spec Acceptance Criteria) **operationalized into `verify:` predicates** — same intent, two faces: `docs/ux` is the **generative** face (*what it should be*, used to design), `docs/qa` the **evaluative** face (*how we prove it is that*, used to accept). This is the error-correction channel — correctness defined and judged *apart from* the act of producing it. Software has a partial ground-truth backstop (the compiler, the tests); a research- or knowledge-shaped lane has none, so there the pre-committed contract + an independent judge is not merely good practice — it is the *only* backstop there is.

**A `doc` lane — the same two contracts, an engine for the umbrella.** A lane that ships prose (copy, docs, research) declares `SAID.surface: doc`, `SAID.reviewers: [doc-editorial]` and `SAID.commands: doc-gate`, and carries the two contracts every lane carries. `docs/ux/feature-ux-rules.md` holds the shape of its artifacts (`R-DOC-*`: a page's section order, front-matter, headings, citation form). `docs/qa/feature-qa-checklist.md` holds its quality bar in the same five-field shape as any lane: `R-QA-01..05`, **one row per engine rule** (closure <=> acceptance, no void source, no exclamation, no banned term, no dangling reference), each `verify:` a grep over the umbrella's log; `R-QA-06`, every Done task has an editorial verdict; `R-QA-07..`, the editorial rules themselves — openable sources, no invented people or figures, what is off-limits — as semantic rows **discharged by the editorial verdict**, never by the operator. The umbrella is the plugin's own engine: `doc-gate` is a **plugin-provided verb**, not a shell command — the skills' command resolution expands it to the shipped `doc-gate.py` with the lane's task log, shippable root and `docs/qa/banned-lexicon.txt`, logged per invocation; the arguments after the verb (`--soft <rule>`, `--off <rule>`) are the lane's whole relaxation, printed on every run, and **every rule off is refused** (exit 2, a config error, never a verdict — the same class as a root that matched nothing). The semantic half is the plugin's `doc-editorial` reviewer: `/said:review-ux` runs it per task at task close and once per feature at Deliver against the checklist's editorial rows; `/said:accept` reads its verdict as recorded evidence; the orchestrator's Eval re-runs the umbrella at HEAD and records both. Nothing is vendored into the project; `claude plugin update` ships every engine fix.

## Hooks

The plugin registers a `SessionStart` hook automatically: after a `/clear` or a compaction inside a SAID lane it re-anchors the session from disk (the feature's status, open run protocols, a re-issue instruction). At a root whose lane block declares a `SAID.lanes:` registry, a branch feature not found there is looked up in each lane the registry lists, and a lane that is its own git repository adds one line for its own branch feature; a directory the registry does not list is never read. The context checkpoint (`SAID.context-checkpoint:` below) is off by default: a session switches it on from its launch line, `SAID_CONTEXT_CHECKPOINT=on claude`, or inside the session with the opt-in word `checkpoint` in the directive (`said! <feature-id> checkpoint`, `flow! <feature-id> checkpoint`), and a session that did neither never checks and never stops. The word makes the skill write an empty marker file `checkpoint-on` in the session scratchpad: a compaction keeps it, a `/clear` does not, so after the stop's own `/clear` re-issue the directive with the word again (the launch-line variable needs nothing). A session that switched it on needs one more piece a plugin cannot install for you: a statusline, the only place a session's context size is visible. Without it the checkpoint stays inactive, and the hook and `said`/`flow` say so once: `context checkpoint inactive: run /said:setup statusline`.

### Install the statusline (one step)

- **With consent:** `/said:setup statusline` shows the exact change, and only after you confirm copies the wrapper to `~/.claude/said-statusline.sh` and sets `statusLine` in `~/.claude/settings.json` (a backup first; no other key touched). `/said:setup` reports the statusline as a ledger row: installed, not installed, or stale.
- **By hand:** copy the plugin's `hooks/said-statusline.sh` to `~/.claude/said-statusline.sh`, then set `"statusLine": {"type": "command", "command": "bash ~/.claude/said-statusline.sh"}`.

The wrapper always runs the newest installed plugin version's statusline script, so a plugin update needs no settings change; never point `statusLine` at a versioned cache path.

## Conventions the skills rely on

- **The `## Lane` block — the binding unit.** Every per-project axis binds in ONE home: a `## Lane` block in your `CLAUDE.md` (per lane; a multi-lane root adds a `SAID.lanes:` registry, one key line of `TOKEN=root` pairs such as `SAID.lanes: [WEB=web/, API=api/]`, each root that lane's directory relative to this file's directory). Fields are hardcoded `SAID.<axis>:` keys — declare once; every skill resolves by key-grep (`grep 'SAID.<axis>:'`), never by prose match: `SAID.lane:`, `SAID.version:` (the starter release this lane was cloned from, `<starter>@<semver>`; optional — an absent key just means unversioned), `SAID.docs-root:`, `SAID.mounts:` (a list read WHOLE: the root or roots where the lane's production lands and what its gate reads, `[path, path]`, or bare `none`; a lane spans its mounts, a mount is not a lane), `SAID.feature-spec:`, `SAID.task-log:`, `SAID.working:`, `SAID.id-shape:` (your own convention, verbatim — a plain `PROJ-01` or a segmented `PROJ-01-BE-07`; recorded, never normalized into sub-fields), `SAID.adr-prefix:`, `SAID.surface:` (the medium — `web|native|cli|api|mcp|audio|doc|...` or `none`; required, no default), `SAID.reviewers:` (the Checkers that gate the surface — a list read WHOLE, like `SAID.lanes:`), `SAID.checkers-dir:` (optional — where your own agent-form Checkers live, if you ship any; omit it and the plugin's own are used), `SAID.commands:` (the umbrella gate command; language-neutral). The `said`/`flow`/`status`/`board` skills read lane state from these keys; the task-log stencil (`template-tasks.md`) derives its id-shape from `SAID.id-shape:`. Single lane -> `said!`; ≥2 task-log-carrying lanes -> `flow!`. **Block shape: the key list carries key lines and nothing else.** Say what the lane is above the keys and how features route below them if you like — but from the first key to the last, every line is a key line, with its whole value on that line: no sub-bullets, no notes beside or under a key, nothing trailing the value. An unanchored `grep 'SAID.<axis>:'` then returns exactly one line for a key and that line is its declaration (a leading `- ` or `*` is fine, so is neither). What you want to say *about* a key belongs in your lane's own docs; the block is the table a skill reads. The list keys `SAID.lanes:`, `SAID.reviewers:` and `SAID.mounts:` sit on one line like every key; they are read WHOLE, and naming them in prose nearby is harmless.
- **Implementation rules — `## Earned rules`.** Your lane's `CLAUDE.md` also carries a `## Earned rules (full context in linked ADR)` section — one non-negotiable per `- ` line with an `R-*` id and a link to its ADR — plus a `## Significant ADRs (skill-referenced)` table (shortname -> your ADR file) and one reminder line under `## Claude Code Reminders`: *before each implementation step, re-read `## Earned rules` and name the ids you apply*. `said:impl` reads the section by heading at Step 0, re-reads it from disk before every confirmation unit, and writes `Rules applied: <ids | none> (block: N)` into each task's `### Fix`; `said:review-qa` verifies that line. **A lane without the `## Earned rules` heading halts `said:impl`** (an empty section is fine — nothing earned yet). Stack conventions (test runner, mocking strategy, file placement) are yours to state there; the engine carries none.
- **`SAID.profile: code | doc | work`** — required. The family of deliverable the lane produces; `said:impl` loads `references/profile-<name>.md` (six slots: `gate, red, carve-out, tag, parity, code-review`) and runs its phases by it. `code` for any lane whose deliverable is source, whatever its surface (`web`, `cli`, `api`, ...); `doc` for a lane gated by `doc-gate`; `work` for a knowledge/work lane with no gate. An absent key or an unshipped name halts `impl` at Step 0 naming the shipped profiles. A new family is one new profile file — the spine and phase files never name a family.
- **`SAID.code-review: on | off`** — optional override; absent = the profile's `code-review` slot (`code` on, `doc`/`work` off). `off` skips `said:impl`'s Phase C generic code-review spawn (logged, never silent) while the lane's declared Checkers still run — the doc surface's own `doc-editorial` reviewer is that lane's review.
- **`SAID.context-checkpoint: <tokens>`** -- optional; the input-token threshold at which `said`/`flow` announce a `CONTEXT-CHECKPOINT` stop at a phase boundary (Implement->Deliver, before debrief, every lane rotate), read from the `context.json` the plugin's statusline script writes. Absent = 300000. The stop is off by default: the threshold applies only in a session switched on by `SAID_CONTEXT_CHECKPOINT=on` or the directive word `checkpoint` (see Hooks), and the key is a number, never the switch. The stop is an operator action (`/clear`, then re-issue the directive; the skill resumes from disk), never an operator question.
- **`SAID.gate-reviewer-threshold: <tokens>`** -- optional; the input-token threshold above which `review-qa`, `accept` and `debrief` hand their reading and classifying steps to the plugin's read-only `gate-reviewer` agent, read at the start of each gate from the same `context.json` the statusline script writes. Absent = 150000. It applies whether or not the context checkpoint (above) is switched on, and it is a separate figure from `SAID.context-checkpoint`. The gate keeps every command, operator pause, verdict and write in the main session; with no figure (no statusline, a null value) the whole gate runs in the main session.
- **Command resolution.** Skills never hardcode `npm`/`bun`/`make`/`cargo`. They resolve the quality-gate command at runtime: `SAID.commands:` (in `CLAUDE.md`) -> `Makefile` -> `package.json` (per lockfile) -> ask you. Make sure your repo exposes one umbrella verifier — or, on a `doc` lane, declare the plugin-provided verb `doc-gate`, which the resolution expands to the shipped engine (the doc lane paragraph above); that lane needs no Makefile and is never asked.
- **Rule labels are the project's, not SAID's.** Skills cite rule labels (shown as `<RULE-LABEL>`) that **your checklists define** — SAID-core ships none of its own. The shipped example checklists include a starting set: gate rules (`R-GATE-*`) and, for `web` list surfaces, wire probes (`R-WIRE-*`). These came from a real `web`-surface project and are a **convention the review machinery expects**, not SAID methodology — keep them (easy path) or rename and rewire the emit-sites. Author your own rules as `<RULE-LABEL>`-shaped entries (see the skeletons).
- **Surface + reviewers.** A lane declares two axes on the `## Lane` block: `SAID.surface:` — the medium it ships (`web|native|cli|api|mcp|audio|doc|...` or `none`; required, set explicitly, never inferred) — and `SAID.reviewers:` — the Checkers that gate that surface (a list read WHOLE; a surface-bearing lane declares ≥1, a `surface: none` lane declares none). The design step (`said:architect`) reads `surface:` to design against the medium; the gate (`said:review-ux`) resolves `reviewers:` and runs each Checker — no hardcoded browser assumption, no engine branch on the medium (see **Scope honesty** for the full triad + guard; `ADR-SAID-S06`).
- **The two contracts — `docs/ux` + `docs/qa`, universal.** Every lane carries both under its docs-root, whatever its surface: `docs/ux` is the **UX / representation** contract (how the surface presents — screens for `web`, endpoints / error-envelopes for `api`, tool-schemas for `mcp`, flags / exit-codes for `cli`), and `docs/qa` is the **QA / evaluation** contract (the checkable bar). Only their *content* varies by `surface:`; their presence never does — so `docs/ux` presence is **not** a signal for anything, and there is no `contract-face` axis to configure. Skills resolve both relative to docs-root.
- **Operator questions and holds.** A task that waits on something only the operator may answer carries `**Blocked-on question:** <id>` (a scope id, else `Q-<n>`); while it is open the task is held -- `impl` does not start or close it and `said`/`flow` stop with `OPERATOR-QUESTION-HELD`. The hold is lifted by one line in the log's `## Lifted holds` section, `- <id> lifted-by: user@WR-<seconds> -- "<verbatim quote>" -- <date> [supersedes: <prior>]`, that cites the operator's answer as a ruling recorded with the `ruled` skill in the work's `rulings.md` (example: `- Q-1 lifted-by: user@WR-1790160000 -- "use the Postgres advisory lock" -- 2026-09-23`). `user` is a fixed role word (the role of the cited answer); the person's name belongs to the ruling. At close, `review-qa/hold-gate.py` checks the cited ruling (provenance typed or dialog, the quote inside the operator's message); old spellings HOLD with a rename message.
- **Fast-track runs.** On your word, a named set of a feature's tasks defers its per-task Deliver gates (review-ux, the code review, review-qa, accept) to one close over the set. `/said:add-task PROJ-01 fast-track "PROJ-01-03 PROJ-01-04"` appends a block to the tasks log, `## Fast-track F01` with the lines `feature:`, `opened:` (the date and HEAD the run opened on), `operator:` (your words quoted with their date, a ruling id when one exists), `tasks:` and an empty `closed:`; run ids count `F01`, `F02` per feature, one open run per feature at a time, a task in exactly one run. A task added while the run is open joins it with the field `**Fast-track:** F01` after `**Refs:**`; the `tasks:` line is never rewritten. The run's close runs the code review in groups you cut, then `review-qa`, `review-ux` and `accept` narrowed to the run, writing `-F01` reports; on all PASS `/said:add-task PROJ-01 fast-track F01 closed` writes the one `closed:` line (date, HEAD, the report names). The block is a recorded skip of per-task gates in your words; said checks no transcript for it.
- **Debrief places the rulings.** `said:debrief` reads the feature's `rulings.md`, the list the hold gate reads, with its own bundled reader. It shows every `pending` ruling for the operator to place, applies a `landed` mark itself once it has opened the ruling's home and checked that it holds the ruling (the session's own action with the installed rulings tool; debrief never writes the list), prints a `rejected` or `superseded` mark line for you to type (in a supervised run the supervisor answers the rows and you review the close footer), and counts the rulings in the close footer's `Rulings:` line. Without the `ruled` skill there is no list: debrief prints `warn: no rulings list` and continues.
- **Placeholders.** Skill text uses `<PROJECT>`, `<ADR-ID>`, `<RULE-LABEL>`, `<entity>`, `<feature-path>`, `<FEAT-ID>` — your binding table + docs supply the concrete values.
